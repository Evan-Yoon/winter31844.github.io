“Tokit”은 나쁘지 않지만, 지금 구조를 보면 단순 토큰 도구가 아니라
프롬프트를 재구성하는 컴파일러 + 비용 최적화 레이어라서 이름이 약간 가벼워 보일 수 있습니다.

설명 없이도 의미가 전달되려면
👉 “압축 / 변환 / 최적화 / 흐름 제어” 느낌이 바로 와야 합니다.

1. 방향 먼저 잡기 (중요)

지금 프로젝트 성격상 이름은 크게 4가지 축 중 하나로 가는 게 좋습니다:

컴파일/변환 느낌
압축/효율 느낌
흐름/파이프라인 느낌
보이지 않는 레이어 느낌
2. 설명 없이 먹히는 이름 (추천 위주)
✔ 가장 추천 (지금 컨셉에 잘 맞음)
1. Prism
의미: 빛을 분해 → 구조화
느낌: 입력을 분석해서 재구성
장점: 짧고 강함, 설명 필요 없음
2. Weave
의미: 엮는다 / 구조화한다
느낌: task graph + context 재조합
Tokit보다 훨씬 “시스템 느낌” 있음
3. Flux
의미: 흐름, 변화
느낌: 입력 → 출력 흐름 제어
CLI + pipeline 이미지랑 잘 맞음
4. Kernel
의미: 핵심 처리 레이어
느낌: LLM 앞단 엔진
기술 느낌 강함 (포트폴리오에 유리)
5. Forge
의미: 다듬고 단련한다
느낌: raw prompt → 최적 prompt
개발자들이 직관적으로 이해함
✔ “토큰 최적화” 살리면서 센스 있는 이름
6. Tess
token + compress 느낌 (암시적)
짧고 기억 쉬움
7. Nexel
next + pixel (작게 쪼갠 단위)
“토큰 단위 최적화” 느낌
8. Mintra
minimize + infra
약간 스타트업 느낌
9. Trim
자른다, 다듬는다
기능이 직관적으로 드러남
✔ “프롬프트 컴파일러” 강조
10. Promptor
prompt + processor
너무 직관적이라 오히려 단점일 수도 있음
11. Compel
compile + propel
의미: 밀어넣고 최적화
12. Parsel
parse + kernel 느낌
분석 → 구조화 이미지

1. 2주 안에 만들 수 있는 “좋은 버전”

목표

한국어 개발자 프롬프트를 coding LLM용 영어 명령 프롬프트로 자동 재작성하고,
입력 토큰과 예상 출력 길이를 줄이는 컴파일러

이건 이미 프로젝트 정의와도 맞습니다.
“번역”이 아니라 “압축 + 재작성 + 출력 제어”라는 포지셔닝이 핵심이고, 그 범위는 2주 MVP로 충분히 설계 가능합니다.

2. 2주 MVP에서 구현 가능한 기능 범위
A. 반드시 구현 가능한 것
1) 한국어 개발 프롬프트 전처리
공백 정리
군더더기 제거
/, @, ! pass-through
코드블록, 파일경로, 에러 메시지 보호
너무 짧은 입력은 그대로 통과

이건 문서에 적힌 코드 로직 레이어 범위 그대로라 2주 안에 충분합니다.

2) 작업 유형 분류

예를 들면:

debug
review
refactor
explain
test
generate

이 정도 5~6개면 충분합니다.
정교한 ML 분류기까지 안 가도 rule + 소형 LLM 조합이면 됩니다.

3) 영어 프롬프트 컴파일

예:

“이 에러 원인 찾아주고 고쳐줘”
→ Identify the root cause and suggest a fix.
“이 코드 리뷰해줘, 중요한 문제만”
→ Review this code and list up to 3 critical issues.

이 부분은 문서에서 이미 작업 유형별 정책 초안이 잡혀 있어서 구현 난도가 낮습니다.

4) 출력 길이 제어
keep it concise
only root cause and fix
in up to 3 bullet points

이건 구현도 쉽고 데모 효과가 큽니다.
출력 토큰 절감의 핵심이기도 합니다.

5) 토큰 비교 기능
원본 입력 토큰
컴파일 후 입력 토큰
응답 토큰
총합 비교

이게 있어야 프로젝트가 “도구”가 아니라 “검증된 시스템”처럼 보입니다.

B. 잘하면 가능한 것
6) 멀티태스크 분해

사용자 입력:

“TypeScript로 JWT 미들웨어 만들어주고, 보안 리뷰하고, 테스트 코드도 써줘”

이걸

shared_context
tasks
dependency

로 나누는 것.
이미 당신 문서에 구조가 꽤 잘 잡혀 있습니다.

2주 안에 가능한 범위는:

완벽한 task graph ❌
기본적인 2~3단계 분해 ⭕

즉:

code_generation
review
test_creation
정도까지는 충분히 됩니다.
7) 간단한 JSON intermediate state

예:

{
  "intent": "multi_step_dev_request",
  "shared_context": {
    "language": "typescript",
    "feature": "JWT authentication middleware"
  },
  "tasks": [
    { "type": "code_generation" },
    { "type": "security_review" },
    { "type": "test_creation" }
  ]
}

이 정도면 발표할 때 매우 강합니다.
다만 이걸 실제 agent orchestration까지 연결하려고 하면 시간이 부족합니다.

8) benchmark 모드

같은 입력에 대해:

원본 프롬프트 결과
컴파일 프롬프트 결과

를 비교해서 토큰 수 / 응답 길이 / 간단한 품질 점수 출력.

이건 2주 프로젝트에서 제일 “있어 보이는” 기능입니다.

C. 2주 안에 넣을 수는 있지만 욕심 영역
9) 세션 요약

한두 턴 정도의 간단한 session memory:

이전 요청의 요약만 유지
다음 턴에 필요한 것만 전달

가능은 하지만, 여기서부터는 품질 리스크가 큽니다.

10) 캐싱

동일하거나 유사한 프롬프트에 대해

이전 컴파일 결과 재사용

기술적으로는 쉬운데, 2주 MVP에선 없어도 됩니다.
넣으면 “서비스스러움”이 올라가는 정도입니다.

역할: 사용자 터미널 환경과 직접 맞닿는 인터페이스를 개발하고, 기존 명령어(/, @, !)의 Pass-through 로직, 파일 시스템 접근(로그, 파일 경로 파싱 등)을 구현합니다.
핵심 과제: 모델이 아무리 똑똑해도 CLI 환경에서 버그가 나면 쓸 수 없습니다. OS 환경(Mac, Ubuntu 등)에 따른 에러 제어와 터미널 내 예쁜 UI(가독성) 출력을 담당합니다.

느낀점

처음에는 단순한 프로젝트로 보였지만, 실제로는 설계와 방향성이 더 중요한 프로젝트라는 것을 느낌
기능 구현보다 “차별화와 설득력”이 더 중요하다는 점을 체감
방향을 잘못 잡으면 평범한 프로젝트가 될 수 있다는 것을 인지함
https://evan-yoon.com/posts/tokit-extra-structure-differentiation-priority/ 여기서 전체 코드 재출력 대신 diff/patch 중심으로 유도하기 이게 무슨 뜻이야?

핵심만 말하면 이 뜻입니다:

코드를 조금만 수정할 때도 전체 코드를 다시 출력하지 말고,
바뀐 부분만 출력하도록 유도하자

예로 보면 바로 이해됨
❌ 기존 방식 (지금 대부분 LLM)

100줄 코드에서 2줄만 수정해도:

// 전체 100줄 코드 다시 출력
function login() {
  ...
}

👉 문제

출력 토큰 엄청 많이 씀
비용 증가
불필요한 정보 반복
⭕ diff / patch 방식
- const token = "abc";
+ const token = process.env.JWT_SECRET;

👉 또는

// 변경된 부분만
function login() {
  const token = process.env.JWT_SECRET;
}
왜 중요한지
기존 구조 문제
작은 수정 → 전체 코드 재출력
출력 토큰 폭발
반복 작업에서 비용 계속 증가
diff 방식 효과
출력 토큰 ↓↓↓
필요한 정보만 전달
반복 작업 최적화됨
Tokit에서 의미

이건 단순 기능이 아니라:

“출력 토큰을 줄이는 핵심 전략 중 하나”

한 줄 정리

“전체를 다시 쓰지 말고, 바뀐 부분만 쓰게 만들어라”

추가로 한 단계 더 정리하면
LLM: 전체 코드 생성 잘함
Tokit: 불필요한 출력을 줄이게 컨트롤

이게 들어가면:

👉 “프롬프트 최적화 도구”에서
👉 “개발 workflow 최적화 시스템”으로 올라감

필요하면
👉 “이걸 실제로 CLI에서 어떻게 구현하는지”도 바로 코드 수준으로 설명해줄게

diff 방식은 알겠는데 patch 방식이 뭐야?

간단히 말하면:

diff = “뭐가 바뀌었는지 보여주는 것”
patch = “그걸 실제로 적용할 수 있는 형태”

1. diff vs patch 차이
✔ diff (설명용)
- const token = "abc";
+ const token = process.env.JWT_SECRET;

👉 의미:

사람이 보기 좋음
변경 내용 “설명”
✔ patch (적용용)
--- a/auth.js
+++ b/auth.js
@@
- const token = "abc";
+ const token = process.env.JWT_SECRET;

👉 의미:

어느 파일의 어디를 바꾸는지 포함
자동으로 코드에 적용 가능
2. 쉽게 비유
diff = “여기 이렇게 바꿔야 해요”
patch = “버튼 누르면 자동으로 바뀌는 것”
3. 왜 Tokit에서 중요하냐

기존 방식:

전체 코드 다시 출력

👉 문제:

토큰 낭비
사람이 복붙해야 함

patch 방식:

변경 부분만
자동 적용 가능

👉 효과:

출력 토큰 ↓↓↓
개발 속도 ↑
반복 작업 최적화
4. Tokit 관점에서 한 줄

diff는 “출력 최적화”,
patch는 “실행 가능한 최적화”

다중 요청에서 우선순위를 정하는 기준

프롬프트에 여러 작업이 들어오면, 먼저 작업을 이런 식으로 나눕니다.

예:

“JWT 미들웨어 만들고, 리뷰하고, 테스트도 추가해줘”

추출된 작업:

code_generation
code_review
test_creation

그 다음 우선순위는 보통 아래 기준으로 정합니다.

우선순위 판단 기준
1) 의존성

가장 중요합니다.

리뷰는 보통 생성 이후
테스트도 보통 생성 이후
수정은 리뷰 이후

즉:

선행 작업이 필요한 것은 뒤로
다른 작업의 입력이 되는 것은 앞으로

예:

code_generation > code_review > test_creation
2) 사용자 명시 순서

사용자가 말한 순서를 존중합니다.

예:

“생성 후 리뷰와 테스트”
“먼저 원인 분석하고, 그 다음 수정해줘”

이런 표현은 강한 힌트입니다.

3) 작업 타입의 성격

일반적으로 이런 우선순위 경향이 있습니다.

분석/원인 파악
생성/수정
검토/리뷰
검증/테스트
문서화

단, 항상 이 순서는 아니고 의존성과 함께 봐야 합니다.

4) 차단 해소 여부

현재 진행을 막는 작업이면 우선순위를 높입니다.

예:

테스트가 다 깨지는 상태면 원인 분석이 먼저
코드가 없는데 리뷰부터 할 수는 없음
5) 비용 대비 효과

토큰 절약 프로젝트에서는 중요합니다.

예:

바로 핵심 원인 분석부터 하면 긴 반복을 줄일 수 있음
문서화는 나중으로 미뤄도 흐름에 영향이 적음
우선순위는 모델이 할까, 코드가 할까
추천 구조: 하이브리드
코드가 해야 하는 것
기본 task dependency graph 생성
명백한 선후관계 판별
사용자 명시 순서 반영
규칙 기반 우선순위 점수 계산
모델이 해야 하는 것
애매한 자연어 해석
암묵적 의도 파악
충돌하는 우선순위 중 의미상 더 중요한 것 선택
요약된 목적 기반 재정렬
