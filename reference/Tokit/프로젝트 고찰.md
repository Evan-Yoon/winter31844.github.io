# 프로젝트 고찰

### 1. 절약 대상이 무엇인가

- 사용자 입력?
- 시스템 프롬프트?
- 에이전트 중간 상태?
- 툴 출력?
- 대화 히스토리?
- 로그?

이걸 구분해야 합니다.

---

### 2. 절약 방식이 무엇인가

- 제거
- 요약
- 치환
- 구조화
- 캐싱
- 재사용
- 중요도 기반 선택

---

### 3. 절약 단위가 무엇인가

- 요청 1회 기준
- 세션 전체 기준
- 에이전트 루프 전체 기준
- 장기 대화 기준

보통 진짜 효과는 **1회 요청보다 반복 루프**에서 큽니다.

---

### 4. 절약의 한계선은 어디인가

어느 선까지 줄여도 괜찮고,

어디서부터 품질이 무너지는지 알아야 합니다.

이게 없으면 최적화가 아니라 그냥 손실 압축이 됩니다.

### 반드시 깊게 봐야 하는 것

- 토큰이 실제로 많이 드는 구간 분석
- 절약 방식별 장단점 비교
- 품질 손실 없는 압축 기준
- 반복 작업에서 누적 절감 효과
- 측정 지표 설계

### 나중에 깊게 봐도 되는 것

- 모델별 tokenizer 차이 세부 연구
- 초미세 prompt packing 기법
- long-context 아키텍처 비교의 극한 최적화
- 추론 토큰과 응답 토큰 상호작용의 정밀 분석

## **접근 방법**

### 1단계: 낭비 지점 찾기

실제 입력을 수집해서

- 어디가 가장 비대한지
- 어떤 유형이 반복되는지
분석

### 2단계: 절약 전략 3~5개 정의

예:

- 중복 제거
- 히스토리 요약
- 툴 출력 압축
- 중요 정보만 유지
- 캐시 재사용

### 3단계: 품질 훼손 여부 측정

- 성공률
- 정확도
- 재시도율
- 사용자 체감 품질

### 4단계: 프로젝트의 핵심 메시지 정리

예:

- “무조건 줄이는 도구”가 아니라
- “작업 성공률을 유지하며 토큰을 절약하는 시스템”

## **기존 LLM 서비스(ChatGPT, Gemini등)들과의 비교 및 고찰**

>> 이미 LLM 서비스들에서 해당 기능들이 강력하게 구현되어있을텐데 차별점 및 방향성을 어떻게 해야할지?

잘못 만들면 “이미 모델이 하는 최적화 위에 또 하나를 얹는 중복 계층”이 되어, 품질만 떨어지고 비용·지연은 늘어나는 구조

### 결론

> **“중복이 될 수도 있지만, 제대로 설계하면 오히려 모델 내부 최적화를 ‘보완’하는 레이어가 된다.”**
> 

핵심은 **대체(replace)가 아니라 보완(augment)**입니다.

### 중복처럼 보이는 이유

OpenAI, Google 같은 곳의 LLM은 이미:

- 컨텍스트 압축
- 중요 정보 선택
- attention 기반 정보 필터링
- 내부 토큰 효율화

를 **모델 내부에서 자동으로 수행**합니다.

그래서 겉보기에는:

> “굳이 또 줄일 필요 있나?”
> 

라는 의문이 생깁니다.

# 중요한 차이

## 1. 모델은 “비용”을 최적화하지 않는다

모델의 목표는:

- 더 정확한 답
- 더 자연스러운 답
- 더 높은 성공률

이지, **토큰 비용 최소화가 목표가 아닙니다.**

## 2. 모델은 “시스템 전체”를 모른다

모델은 한 요청 단위로만 판단합니다.

하지만 너의 프로젝트는:

- 여러 번의 agent loop
- 반복되는 tool 호출
- 누적되는 컨텍스트
- 세션 전체 흐름

👉 즉 **“시간 축 전체” 최적화 문제**입니다.

## 3. 모델은 “외부 데이터 품질”을 통제 못함

특히 이런 경우:

- 툴 출력 (logs, HTML, JSON)
- 코드 베이스 일부
- API 응답
- 크롤링 결과

이건 대부분 **불필요하게 크고 더럽습니다.**

👉 모델은 이걸 그대로 받아서 처리해야 함

👉 너는 **들어가기 전에 줄일 수 있음**

---

## **가장 중요한 차별 포인트**

## ❌ 잘못된 방향 (중복됨)

- 프롬프트를 그냥 줄이기
- 모델 입력을 무작정 요약
- 자연어를 더 짧게 바꾸기

👉 이건 모델이 이미 잘함 → 중복 + 품질 저하

---

## ✅ 좋은 방향 (보완)

### 1. “모델이 보기 전에” 정리

- 툴 출력 정제
- 로그 압축
- HTML → 구조화 데이터 변환
- 불필요 필드 제거

👉 이건 모델이 못하는 영역

---

### 2. 반복 루프 최적화

- 이전 결과 캐싱
- 중복 요청 제거
- 동일 context 재사용
- diff 기반 업데이트

👉 이건 agent 레벨 최적화

---

### 3. 정보 중요도 기반 선택

- 전부 요약 ❌
- 중요한 것만 유지 ⭕

예:

- 에러 메시지 → 유지
- stack trace 일부 → 축소
- 성공 로그 → 제거

---

### 4. 구조화 압축 (핵심)

자연어 대신 구조화:

```
{
  "error": "TypeError",
  "file":"auth.ts",
  "line":42
}
```

👉 토큰 ↓ + 의미 유지 ↑

# ⚖️ “중복 vs 보완” 판단 기준

이 질문으로 판단하면 됩니다:

### 👉 이 최적화가 모델 없이도 의미가 있는가?

- YES → 가치 있음 (보완)
- NO → 중복 가능성 높음

| 작업 | 평가 |
| --- | --- |
| 긴 문장 줄이기 | ❌ 모델이 잘함 |
| JSON 정리 | ⭕ 가치 있음 |
| 로그 필터링 | ⭕ 매우 중요 |
| 히스토리 요약 | ⚠️ 상황 따라 다름 |
| 캐싱 | ⭕ 모델이 못함 |

## MVP 방향 추천

### 1. 로그/툴 출력 최적화

- 가장 효과 큼
- 모델이 못함
- 바로 성과 나옴

---

### 2. 반복 작업 캐싱

- agent loop에서 핵심
- 비용 절감 크게 발생

---

### 3. diff 기반 context 전달

- 전체 대신 변화만 전달

---

### 4. 중요도 필터

- rule + LLM 혼합 가능

## **유저가 프롬프트를 하나의 개발 카테고리 키워드가 아닌 여러 작업을 요청했을 경우**

ex) "코드생성", "리뷰", "테스트" 와 같은 여러 작업을 요청했을 때

**단일 분류기**로 보면 안 되고, **“복합 작업 요청을 작업 그래프(task graph)로 분해하는 문제”**

즉 유저 입력이

- 코드 생성
- 리뷰
- 테스트

를 동시에 담고 있다면, 이것은 **카테고리 1개 선택**이 아니라

**의도(intent) + 작업들(tasks) + 실행순서(order) + 공유 컨텍스트(shared context)** 를 추출해야 합니다.

핵심은 두 가지입니다.

1. **의미를 잃지 않게 분해**
2. **중복 컨텍스트를 줄여 토큰 절약**

기존 방식(단 하나의 카테고리로 분류) → 정보 손실

```jsx
{ "category": "code_generation" }
```

단일 분류 방식이 아닌 멀티태스크 방식 추출

```jsx
{
  "intent": "multi_step_dev_request",
  "tasks": [
    { "type": "code_generation" },
    { "type": "code_review" },
    { "type": "test_creation" }
  ]
}
```

## **복합 요청을 처리하기 위한 구조**

## 1단계: 최상위 의도 분류

이 요청이 무엇인지 먼저 판단

예:

- 질문형
- 디버깅형
- 멀티스텝 개발형
- 문서화형

여기서는:

```
{
  "intent":"multi_step_dev_request"
}
```

---

## 2단계: 작업 추출

문장 안에 포함된 작업들을 뽑기

```
{
  "tasks": [
		"code_generation",
		"code_review",
		"test_creation"
  ]
}
```

---

## 3단계: 관계 추출

작업들이 서로 어떤 관계인지 추출

```
{
  "execution_plan": [
    {
      "task":"code_generation",
      "depends_on": []
    },
    {
      "task":"code_review",
      "depends_on": ["code_generation"]
    },
    {
      "task":"test_creation",
      "depends_on": ["code_generation"]
    }
  ]
}
```

이 단계가 중요합니다.

왜냐하면 **토큰 절약은 분류보다 “중복 처리 제거”에서 더 크게 나오기 때문**입니다.

---

# 3. 의미 유지의 핵심은 “공유 컨텍스트”를 따로 뽑는 것

복합 요청에서 가장 흔한 비효율은 각 작업이 같은 맥락을 매번 다시 받는 것입니다.

예를 들어 유저가:

> “Node.js로 JWT 인증 미들웨어를 만들어주고, 보안 리뷰도 해주고, 테스트 코드도 작성해줘.”
> 

라고 했다면, 세 작업 모두 공통으로 필요한 정보는 사실 비슷합니다.

- 언어: Node.js
- 주제: JWT 인증 미들웨어
- 목표: 구현 + 리뷰 + 테스트

이걸 작업마다 다시 설명하면 토큰이 낭비됩니다.

그래서 분해할 때 이렇게 해야 합니다.

```
{
  "shared_context": {
    "language":"Node.js",
    "feature":"JWT authentication middleware"
  },
  "tasks": [
    {
      "type":"code_generation",
      "task_context": {}
    },
    {
      "type":"code_review",
      "task_context": {
        "focus": ["security","maintainability"]
      }
    },
    {
      "type":"test_creation",
      "task_context": {
        "framework":"jest"
      }
    }
  ]
}
```

즉:

- **공통 정보는 shared_context**
- **작업별 차이만 task_context**

이렇게 나누면 의미 유지와 토큰 절약이 동시에 됩니다.

---

# 4. 성능 유지하면서 토큰 줄이려면 “한 번에 다 하지 말고 상태를 축적”해야 함

복합 작업을 처리할 때 나쁜 방식은 이겁니다.

## 비효율적인 방식

각 단계마다 전체 원문 프롬프트를 다시 넣는 것

- 코드 생성할 때 전체 프롬프트
- 리뷰할 때 전체 프롬프트 + 생성 결과
- 테스트할 때 또 전체 프롬프트 + 생성 결과 + 리뷰 결과

이러면 컨텍스트가 눈덩이처럼 커집니다.

---

## 더 좋은 방식

각 단계의 산출물을 **정규화된 상태(state)** 로 저장하고, 다음 단계에는 필요한 것만 전달

예:

```
{
  "state": {
    "user_goal":"JWT auth middleware",
    "generated_code_summary": {
      "files": ["authMiddleware.js"],
      "key_points": [
"verifies bearer token",
"extracts user id",
"rejects expired token"
      ]
    },
    "review_findings": [
"secret hardcoded risk",
"missing malformed token handling"
    ]
  }
}
```

그 다음:

- 리뷰 단계에는 전체 코드 대신 코드 + 최소 요구사항
- 테스트 단계에는 전체 대화 대신 최종 코드 구조 + 리뷰에서 나온 위험 포인트

이렇게 넘깁니다.

---

# 5. 토큰 절감을 위한 실제 전략

## 전략 A: 작업을 “순서”와 “출력물” 기준으로 분리

각 작업은 다음 2가지를 명확히 가져야 합니다.

- 이 작업의 입력
- 이 작업의 출력

예:

### code_generation

입력:

- shared_context
- feature requirements

출력:

- generated_code
- short summary

### code_review

입력:

- generated_code
- review focus

출력:

- findings
- patch suggestions
- review summary

### test_creation

입력:

- generated_code
- critical findings

출력:

- test cases
- test code

이렇게 하면 각 단계에 불필요한 히스토리를 안 넣어도 됩니다.

---

## 전략 B: 긴 자연어 대신 구조화 상태 사용

예를 들어 리뷰 결과를 길게 자연어로 유지하지 말고:

```
{
  "review_findings": [
    {
      "type":"security",
      "severity":"high",
      "message":"JWT secret is hardcoded"
    },
    {
      "type":"error_handling",
      "severity":"medium",
      "message": "Malformed token case not handled"
    }
  ]
}
```

이렇게 보관하면 다음 테스트 단계에서 필요한 부분만 쉽게 꺼낼 수 있습니다.

---

## 전략 C: “전부 전달”이 아니라 “필요한 부분만 전달”

예를 들어 테스트 생성에는 리뷰의 전체 문장보다 이런 것만 필요합니다.

- 실패 가능 시나리오
- 엣지 케이스
- 보안 관련 경계 조건

따라서 리뷰 전체를 넣지 말고:

```
{
  "test_targets": [
    "expired token",
    "malformed token",
    "missing authorization header"
  ]
}
```

로 축약해서 전달하면 됩니다.

---

## 전략 D: 중간 요약은 “의미 압축”이어야지 “문장 축소”가 아님

토큰 절약에서 흔한 실패는 중간 결과를 대충 짧게 줄이는 것입니다.

예를 들어:

- 나쁜 요약: “JWT 관련 코드 생성 및 리뷰 완료”
- 좋은 요약: “Bearer token 파싱, 만료 검증, 사용자 ID 추출 구현됨. malformed token 처리 누락.”

좋은 요약은 **다음 단계 의사결정에 필요한 정보만 남긴 요약**입니다.

---

# 6. 추천 분류 구조

네 프로젝트라면 이런 형태가 제일 실용적입니다.

```
{
  "intent":"multi_step_dev_request",
  "shared_context": {
    "domain":"backend",
    "language":"typescript",
    "feature":"JWT auth middleware"
  },
  "tasks": [
    {
      "id":"t1",
      "type":"code_generation",
      "priority":1,
      "depends_on": []
    },
    {
      "id":"t2",
      "type":"code_review",
      "priority":2,
      "depends_on": ["t1"],
      "focus": ["security","robustness"]
    },
    {
      "id":"t3",
      "type":"test_creation",
      "priority":3,
      "depends_on": ["t1","t2"]
    }
  ]
}
```

이 구조의 장점은:

- 다중 작업 보존
- 순서 보존
- 중복 제거 가능
- 후속 라우팅 쉬움

# 7. 성능을 유지하려면 “압축 금지 구간”도 정해야 함

토큰 절약만 생각하면 모든 걸 요약하고 싶어지는데, 그러면 품질이 망가질 수 있습니다.

복합 개발 작업에서 보통 압축하면 안 되는 것:

- 실제 생성된 코드 본문
- 에러 메시지 원문
- 테스트 실패 로그의 핵심 부분
- 보안 리뷰에서 발견된 구체 이슈
- 함수 시그니처 / 인터페이스

압축해도 되는 것:

- 반복된 사용자 배경 설명
- 이미 해결된 이전 논의
- 중요도 낮은 리뷰 코멘트
- 성공 로그
- 중복된 코드 설명

즉 **원본 유지가 필요한 아티팩트와 요약 가능한 메타정보를 분리**해야 합니다.

---

# 8. 가장 추천하는 운영 방식

## 입력 분석 단계

유저 프롬프트를 받아서:

- shared_context 추출
- tasks 추출
- dependency 추출
- output contract 정의

---

## 실행 단계

각 task를 개별적으로 실행하되, 이전 단계의 전체 대화가 아니라 **state** 만 참조

---

## 상태 압축 단계

매 단계 후:

- 원본 결과는 저장
- 다음 단계용으로는 summary/state만 전달

---

## 최종 응답 단계

최종 출력은 유저 입장에서 다시 합쳐서 보여줌

즉 내부적으로는 분해, 외부적으로는 통합입니다.

---

# 9. 한 줄로 정리하면

이 문제는 **“멀티라벨 분류”만으로는 부족하고, “작업 분해 + 공유 컨텍스트 분리 + 상태 기반 전달”**로 풀어야 합니다.

---

# 결론

유저가 “코드생성, 리뷰, 테스트”처럼 여러 작업을 함께 요청하면:

1. **하나의 카테고리로 분류하지 말고**
2. **복합 개발 요청으로 판별한 뒤**
3. **작업 목록 + 순서 + 의존성 + 공유 컨텍스트를 추출하고**
4. **각 단계에는 전체 대화가 아니라 필요한 상태만 전달**해야 합니다.

그렇게 해야:

- 의미 손실 없이
- 성능을 유지하고
- 중복 컨텍스트를 줄이면서
- 토큰 사용량을 낮출 수 있습니다.

필요시 single → multi 승격

ex) 처음엔 “리뷰해줘”였는데 실제론 “수정안도 제시하고 테스트도 작성”이 필요함

판단 기준

다음이면 보통 **single**입니다.

- 핵심 동사 1개
- 결과물 1개
- 의존성 없음
- 후속 작업 암시 약함

다음이면 보통 **multi**입니다.

- 동사 2개 이상
- 결과물 2개 이상
- “그리고”, “후에”, “같이”, “까지” 같은 연결
- 생성 + 리뷰 + 테스트처럼 성격이 다른 작업 결합
- 순서가 중요함

한가지 예외

아주 가벼운 복합 요청의 경우 full multi까지 필요 없음

ex) “설명하고 예시도 하나 보여줘”

최종 단계 구별

- `single`: 코드 리뷰만
- `light_multi`: 설명 + 간단한 예시
- `full_multi`: 코드 생성 + 리뷰 + 테스트 + 수정안

LLM-cli와 tokit-cli 의 세션 차이

CLI 자체 세션은 보통 이런 걸 다룹니다.

- 대화 이어가기
- 최근 히스토리 복구
- 프로젝트별 컨텍스트 유지

반면 tokit이 따로 가져갈 수 있는 건 이런 종류입니다.

- 현재 **어느 CLI를 쓰고 있는지**
- CLI를 바꿀 때 넘길 **최소 요약 상태**
- 긴 로그에서 추린 **실무용 핵심 결과**
