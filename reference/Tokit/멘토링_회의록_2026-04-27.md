## 1. 경량성 vs 정확도 트레이드오프

### 팀의 고민

- CLI 도구 특성상 실행 속도와 경량성이 중요하다고 판단해 소형 모델 채택을 시도
- 소형 모델로는 한→영 번역 품질이 기대에 미치지 못함
- 파라미터 수가 높은 모델(3GB+)로 교체 시 성능은 개선되나 메모리 점유율 급증

### 멘토 피드백

- 한국어는 중국어, 일본어와 함께 번역 난이도가 높은 언어 — 영어-스페인어라면 소형 모델로도 충분했을 문제
- **핵심 질문 제시**: "CLI의 목표가 무엇인가?" — 방향 결정이 먼저
  - **경량성 우선**: 로컬 소형 모델 채택 → 정확도를 단계적으로 높여나가는 로드맵
  - **정확도 우선**: API 통신 허용 → Gemini Pro, Claude Sonnet 수준 모델 활용

- **단계별 접근 권고**:
  - 한꺼번에 번역 품질, 개발 용어 보존, 문맥 유지, 지식 충실도 5가지를 동시에 달성하려 하지 말 것
  - 개발 용어 보존 → 번역 품질 순으로 우선순위를 정해 단계적으로 달성
  - 실제 대학원 모델링도 "포기할 것과 챙길 것을 계속 선택하는 과정"

### 결론

- 팀의 원래 기획 의도(CLI 앞단 개입, 경량성 우선) 재확인
- **경량성 우선 방향 유지** → 단계별 정확도 개선 로드맵으로 접근

## 2. 모듈 간 데이터 흐름 책임 소재 기준

### 팀의 고민

- 각 모듈이 독립적이지 않고 서로 핑퐁 방식으로 데이터를 주고받는 구조
- 동일 데이터에 대한 검증/테스트 코드가 여러 모듈에 중복될 경우 비효율 발생 우려
- 어느 위치에서 책임을 가져야 하는지 기준이 불명확

### 멘토 피드백

- 미리 모든 충돌을 예방하는 것은 개발상 불가능 — 충돌 발생 후 대응이 현실적
- **컨버터 패턴 활용 권고**:
  - 우선 합의된 데이터 형태(예: HDMI 형태)로 최대한 맞춰 개발
  - 충돌 발생 시 해당 모듈에 컨버터 함수를 추가해 감싸는 방식으로 대응
  - 2~3일 후 여러 모듈에서 유사한 컨버터가 발견되면 그때 공통 형태 재논의

- **스프린트 단위 관리 방식**:
  - 스프린트 시작 전: 관련자들이 데이터 형태 합의 후 개발 진입
  - 스프린트 중: 합의된 형태 유지
  - 스프린트 종료 후: 문제 발생 사항 논의 및 다음 스프린트 반영

- **주의사항**: 처음부터 하나의 모듈이 모든 것을 관장하도록 고정하면 자유도가 떨어져 오히려 성능 이슈 발생 가능

### 결론

- 완벽한 사전 설계보다 **빠른 통합 후 충돌 발견 → 점진적 개선** 방식 채택
- 현재 Zod 스키마 기반 공용 타입 정의 방향은 유효

## 3. 에러 처리 방식

### 팀의 고민

- 예상 가능한 에러와 예상치 못한 에러(예: 서버 갑작스러운 종료) 처리 방식 고민
- try-catch로 모두 처리할지 vs 결괏값 자체로 성공/실패를 관리할지

### 멘토 피드백

- try-catch와 결괏값 처리는 대립 관계가 아님 — **함께 사용하는 것이 정답**
  - 예외(Exception)는 반드시 try-catch로 잡아야 함
  - catch 블록에서 예외를 죽이지 말고 **리턴 값으로 실패 상태를 반환**
  - 리턴된 성공/실패 결과를 기반으로 CLI에서 사용자에게 어떻게 보여줄지 결정

- **실패 처리 방식 옵션** (기획 판단 사항):
  - 실패 메시지 출력 후 종료
  - catch 블록에서 함수를 재귀 호출로 최대 3회 재시도
  - 기타 리다이렉트 로직

### 결론

- **try-catch + 리턴 값 처리 방식 병행** 채택
- 구체적인 실패 처리 정책(재시도 횟수, 메시지 형태 등)은 통합 테스트 후 팀 논의

## 4. 소형 모델 프롬프트 이탈 문제

### 팀의 고민

- 4.6B 모델에서는 번역 품질이 괜찮음
- 더 작은 모델 사용 시 프롬프트 이탈 발생 — 지시사항 무시, 엉뚱한 답변 반환
- 번역 품질, 개발 용어 보존, 문맥 유지, 지식 충실도 5가지가 동시에 무너짐

### 멘토 피드백

**기술적 해결 방향 3가지 제시**:

1. **파이프라인 분리**: 번역 모델 + 요약 모델을 별도로 운용
   - 3.7GB 단일 모델 대신 300MB 요약 모델 + 100MB 번역 모델 + 100MB 품질 유지 모델 조합
   - 각 모델이 단일 역할만 수행 → 이탈 가능성 감소

2. **프롬프트 재가공**: 입력받은 프롬프트를 그대로 넘기지 않고 코드 레벨에서 특정 키워드를 캐치해 재가공 후 전달

3. **파이프라인 순서 변경**: 한국어로 먼저 처리 → 최종 단계에서 영어로 단순 번역
   - 한국어 이해 모델로 처리 후 번역만 별도 수행
   - 각 순서별 정확도 차이 테스트 필요

- **추가 관점**: 컨텍스트를 과도하게 넘기는 것도 이탈 원인일 수 있음

- **전반적 방향**: 현재 전 세계 AI 논문이 "어떤 순서, 어떤 방식으로 경량화하면서 정확도를 유지할 수 있는가"를 다루는 영역 — 팀 자체 실험과 연구 필요

### 결론

- 시도해볼 방법론 목록 확보
- 파이프라인 분리 + 프롬프트 재가공 방식 우선 실험 예정
- 결과에 따라 타협점 모색

## 5. 로컬 모델 번들링 vs API 통신 — 핵심 대립 해소

### 팀 내 대립 구도

- **경량성 주장**: CLI인데 3GB+ 모델을 설치하게 하는 것은 CLI의 의미 퇴색
- **정확도 주장**: 전체 파이프라인이 정확하게 동작하려면 모델 성능이 필요

### 멘토 핵심 질문

> "CLI 설치할 때 모델을 같이 설치하면 되는 거 아닌가요?"
> "네트워크 없이 써야 하는 이유가 무엇인가요?"

### 멘토 최종 의견

- CLI 설치 시 용량이나 소요 시간을 크게 고민한 적 없음 — 사용자 관점에서 중요하지 않음
- **처음 설치 시 모델 포함 번들링이 UX 관점에서 더 직관적**
  - 게임 설치 후 갑자기 3.7GB 추가 다운로드 요구 → 이탈 발생
  - 처음부터 "4GB CLI" 명시 후 설치 기다리는 것이 자연스러운 경험
- API 통신 성능도 충분히 빠름 (리퀘스트-리스폰스 약 0.5초)
  - 로컬 디바이스에서 4GB 메모리 점유 대비 서버 60GB RAM 처리 + 캐싱이 오히려 빠를 수 있음

### 추가 논의 (메모리 점유 상한선)

- 큰 모델 사용 시 메모리 점유 증가 → 사용 가능 기기 범위 축소
- 오픈 클로드(맥미니 깡통)가 잘 팔렸던 이유: 네트워크만 있으면 Claude Code/Gemini CLI 연결 가능
- 현재 Claude가 Claude Code의 외부 접근 차단 → 로컬 모델 필요성 대두되는 상황

### 멘토 최종 조언

> "엔지니어라면 계속 고민해야 할 것은 메모리 덜 쓰고, 캐시 덜 쓰고, CPU 덜 쓰면서 성능과 정확도가 '나쁘지 않은 수준'인 가성비 구간을 찾는 것"

### 결론

- **로컬 모델 번들링 방식 채택** (CLI 설치 시 모델 포함)
- 단, 타겟 사용자 디바이스 스펙 고려 → 메모리 점유 상한선 설계 필요
- API 통신 방식도 성능 비교 후 병행 고려 가능

## 팀 내 자체 해소 사항

멘토링 중 팀원 간 추가 논의를 통해 자체 해결:

- **서버 운영 고민**: 자체 서버에 모델 올려 호스팅하는 방식은 비용 문제로 제외
- **ollama 활용 방식**: llama.cpp 서버 열어서 사용하는 방식은 별도 검토 중
- **결론**: 자체 서버 호스팅 없이 로컬 모델 번들링 방식으로 확정
