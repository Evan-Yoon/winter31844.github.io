## 3. 세션 아이디 및 실행 모드 정의

### CLI → State & Context로 넘겨줘야 하는 항목

- `session_id` (Optional, 물음표 처리 — 없어도 동작)
- `execution_mode` (현재 stub 모드로 진행 중, 추후 확정)
- `cwd` (현재 작업 디렉터리)
- `timestamp` (시간 정보)

### State & Context에서 관리해야 하는 항목

- `current_task` (현재 작업)
- `completed_tasks` (완료된 작업 목록)
- `next_task` (다음 작업)
- `checkpoint_table` (체크포인트 기록)

### 체크포인트 관련 미결 사항

- 언제 체크포인트를 남길 것인지
- 작업 완료 기준 정의
- CLI가 체크포인트 생성 트리거를 줄 것인지 여부
  → **팀장과 이지호 별도 확인 예정**

### 컨텍스트 압축 관련

- 대화가 길어질 때 컨텍스트 압축 시점 결정 필요
- 최종 결과 vs 오래된 상태 중 우선순위 정책 결정 필요
- `active_files` (활성 문서 결정 정책) 결정 필요
  → **팀장과 이지호 별도 확인 예정**

## 4. Task Graph ↔ State & Context 책임 분담

### 핵심 쟁점 3가지 (AI 제안 기반 논의)

**쟁점 1: TaskGraph 정확한 형식**

- DAG 방식 확정
- Adjacency List vs 기타 방식 논의 중
- **결론**: DAG + Topological Sort 방식으로 확정

**쟁점 2: 순환 참조 검증 책임**

- 옵션 A (윤지현만): 방어 없음
- 옵션 B (이지호만): 매번 검증 → 비효율
- **결론**: 이중 검증 방식으로 분담
  - 윤지현: DAG Topological Sort 시 1차 검증
  - 이지호: Fail-safe 시 2차 검증 (StateValidator)

**쟁점 3: Task 실패 시 의존 Task 처리**

- **결론**: Strict 모드 채택
  - 의존 Task 실패 시 현재 Task 실행 불가
  - 명확한 에러 메시지 출력
  - 사용자가 실패 원인 파악 후 재시도
  - 구체적 에러 케이스는 통합 테스트 후 보완 예정

### 모듈 간 데이터 흐름 (확정)

```
[윤지현] Task Graph 생성 (DAG + Topological Sort)
    ↓
[이지호] TaskGraph 수신 → 세션 상태 확인 → 다음 Task 선택
    ↓
[윤지현] 오케스트레이터 → 다음 실행 Task 결정
    ↓
[이지호] 의존성 결과 선택 → 압축 → ExecutionContext 생성 → 세션 갱신
    ↓ (반복)
```

- **특이사항**: 두 모듈 간 핑퐁 구조 발생 — 협업 특성상 불가피하며 통합 후 최적화 예정
